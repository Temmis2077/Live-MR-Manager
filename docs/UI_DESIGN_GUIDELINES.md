# OSW UI 디자인 가이드라인

> OSW(Open Stem Wave)의 화면을 설계·개편·검수할 때 사용하는 실행 기준서입니다.

이 문서는 새로운 화면을 만들 때의 기준, 기존 UI를 리팩터링할 때의 기준, PR과 릴리즈 전 검수 기준을 함께 정의합니다. 픽셀 단위의 고정된 목업보다 제품의 목적과 반복 가능한 판단 기준을 우선합니다.

## 1. 제품과 브랜드 방향

### 제품 정의

OSW는 음악을 재생하는 앱이 아니라 **스템을 열고, 노래하고, 다시 믹싱하는 오디오 작업 공간**입니다.

- 핵심 사용자: 노래 방송 스트리머와 커버 제작자
- 주요 작업: 곡 추가, 보컬·MR 분리, 가사 싱크, 재생·믹싱, OBS 오버레이
- 장기 방향: 악기별 스템과 내부 믹서가 있는 개방형 미니 DAW
- UI 목표: 프로 오디오 도구의 명확함과 크리에이터 앱의 접근성을 함께 제공

### 브랜드 사용

- 제품명은 `OSW`를 기본으로 사용하고, 처음 등장할 때만 `Open Stem Wave`를 병기합니다.
- `OSW` 워드마크와 행성 마크는 앱 아이콘·사이드바·문서에서 일관되게 사용합니다.
- 브랜드 액센트는 기본적으로 보라색 계열을 사용합니다. 마크와 워드마크가 경쟁하지 않도록 작은 크기에서는 단색 표현을 우선합니다.
- `Live MR Manager`, `Mod`, 내부 빌드명, 개발용 버전 문자열은 릴리즈 사용자 화면에 노출하지 않습니다. 필요하면 About·진단 화면에만 표시합니다.
- `BETA` 표기는 제품의 정체성을 대신하지 않습니다. 베타 상태를 고지해야 하는 경우 제목 옆 작은 상태 표시나 릴리즈 문서에서 제한적으로 사용합니다.

## 2. 시각 언어

### 기본 인상

OSW의 기본 인상은 **어두운 중성 배경 위에 절제된 보라색 액센트를 사용하는 오디오 작업 도구**입니다.

- 정보 위계와 작업 흐름을 장식보다 우선합니다.
- 글래스모피즘은 모달·드롭다운·고정 도크처럼 레이어 분리가 필요한 곳에만 사용합니다.
- 그라디언트는 주요 CTA나 브랜드 마크처럼 제한된 강조에만 사용합니다.
- 글로우는 현재 재생·처리 중·선택 상태처럼 의미가 있는 경우에만 사용합니다.
- 카드 hover에서 확대·상승·강한 글로우를 동시에 적용하지 않습니다. 주변 레이아웃을 흔들지 않는 border·background 전환을 우선합니다.
- 한 화면 안에서 패널·카드·버튼의 밀도와 모서리 규칙을 임의로 섞지 않습니다.

### 라이브 모드와 녹음 모드

> **현재 이 전환은 사용자에게 노출되지 않습니다.** 두 모드를 실제로 가르는 기능
> (악기 분리 등)이 아직 없어 `src/js/events/app-mode-ui.js`의
> `APP_MODE_UI_ENABLED = false`로 첫 실행 선택 모달과 설정 세그먼트를 감춰 뒀습니다.
> `body[data-app-mode]` 게이팅과 아래 원칙은 그대로 두어, 기능 차이가 생기면
> 플래그만 되돌리면 됩니다.

- 라이브 모드는 방송 중 빠른 인식과 편안한 조작을 위해 넉넉한 여백과 라운드를 사용합니다.
- 녹음 모드는 미니 DAW 방향에 맞춰 더 조밀하고 각진 콘솔 톤을 사용합니다.
- 두 모드는 색상 효과를 과하게 달리하지 않습니다. 차이는 여백, 모서리, 정보 밀도, 상태 표현으로 전달합니다.

## 3. 디자인 토큰

실제 구현의 공통 토큰은 `src/styles/base.css`에 정의합니다. 문서의 원칙을 바꿀 때는 CSS 토큰과 함께 검토합니다.

### 색상

| 역할 | 현재 토큰 | 사용 기준 |
| --- | --- | --- |
| 앱 배경 | `--bg-color` | 화면의 기본 배경. 장식용 색을 직접 넣지 않음 |
| 사이드바 | `--sidebar-bg` | 주요 내비게이션 영역 |
| 고정 도크 | `--dock-bg` | 플레이어처럼 화면에 고정된 작업 영역 |
| 표면 단계 | `--surface-1` ~ `--surface-3` | 같은 화면 안의 깊이와 hover 표현 |
| 구분선 | `--glass-border` | 구조를 나누되 시선을 끌지 않음 |
| 본문 | `--text-main` | 제목과 주요 정보 |
| 보조 텍스트 | `--text-muted` | 설명·메타 정보 |
| 약한 텍스트 | `--text-dim` | 라벨·placeholder·비활성 상태 |
| 주요 액센트 | `--accent-primary` | primary action·선택·현재 상태 |
| 보조 액센트 | `--accent-secondary` | 액센트의 보조 단계 |
| 성공·경고·오류 | 의미별 상태색 | 액센트 보라와 혼용하지 않음 |

현재 기본 다크 테마의 브랜드 기준은 `--accent-primary: #8b5cf6`, `--accent-secondary: #a78bfa`입니다. 라이트·핑크·스카이 테마도 동일한 역할 토큰을 사용하며, 색상값만 직접 재정의합니다.

색상만으로 상태를 표현하지 않습니다. 상태색은 텍스트, 아이콘, 배지, 진행률 또는 보더 중 하나 이상과 함께 사용합니다.

### 간격

4px 기반의 간격 체계를 사용합니다.

| 단계 | 값 | 권장 용도 |
| --- | ---: | --- |
| `xs` | 4px | 아이콘과 텍스트 사이의 최소 간격 |
| `sm` | 8px | 배지·컨트롤 내부, 관련 요소 묶음 |
| `md` | 16px | 일반 컨트롤 사이, 카드 내부 |
| `lg` | 24px | 섹션 내부, 주요 그룹 사이 |
| `xl` | 32px | 큰 섹션 사이, 화면 안전 여백 |
| `2xl` | 40px 이상 | 화면 시작·끝의 넉넉한 여백 |

특정 화면에서만 사용하는 임의의 간격을 추가하기 전에 기존 단계로 해결할 수 있는지 확인합니다.

### 모서리와 크기

- 작은 컨트롤: 6~8px
- 일반 버튼·입력: 8~10px
- 카드·패널: 라이브 모드 12~14px, 녹음 모드 8~10px
- 모달·플로팅 메뉴: 12~16px
- 완전한 원형은 아바타, 재생 버튼, 상태 점처럼 원형 의미가 있는 요소에만 사용합니다.

현재 코드의 기준 토큰은 `--radius-nav`, `--radius-card`, `--btn-h-sm`, `--btn-h-md`, `--btn-h-lg`, `--btn-h-xl`입니다. 새로운 높이 단계를 만들기보다 먼저 이 토큰을 재사용합니다.

### 타이포그래피

- 기본 글꼴은 프로젝트에 포함된 `SUITE`를 사용합니다.
- 화면 제목은 굵고 짧게, 설명은 한 단계 낮은 대비와 굵기로 표시합니다.
- 제목·본문·보조 문구 사이에 크기뿐 아니라 굵기와 색상 차이를 함께 사용합니다.
- 긴 설명을 배지나 버튼 안에 넣지 않습니다.
- 대문자 영문 라벨과 과도한 자간은 보조 라벨에만 제한적으로 사용합니다.

### 레이어와 효과

레이어 순서는 일반 화면 → 고정 도크 → 드롭다운·컨텍스트 메뉴 → 모달 → 전역 알림 순으로 정의합니다. `z-index`는 컴포넌트의 의미에 따라 관리하고 임의의 큰 값을 반복해서 추가하지 않습니다.

- 블러는 배경과 레이어를 분리해야 할 때만 사용합니다.
- 그림자는 깊이를 설명하는 정도로 사용하고, 모든 카드에 강한 그림자를 적용하지 않습니다.
- 애니메이션은 기본적으로 짧은 `opacity`, `border-color`, `background-color` 전환을 사용합니다.
- 정보를 전달하지 않는 반복적인 pulse·float·glow 애니메이션은 사용하지 않습니다.
- `prefers-reduced-motion` 환경에서는 이동과 반복 애니메이션을 줄입니다.

## 4. 컴포넌트 가이드

모든 인터랙티브 컴포넌트는 최소한 기본, hover, focus, active, disabled, loading 상태를 검토합니다. 오류나 삭제처럼 위험한 동작에는 destructive 상태도 정의합니다.

### 버튼

- `Primary`: 화면의 핵심 행동 하나에만 사용합니다. 예: `노래 추가`, `자동 정렬`, `저장`.
- `Secondary`: primary를 보조하는 일반 행동에 사용합니다.
- `Quiet`: 탐색·닫기·보조 설정처럼 시각적 우선순위가 낮은 행동에 사용합니다.
- `Destructive`: 삭제·초기화·취소처럼 되돌리기 어려운 행동에 사용하며, 확인 단계를 제공합니다.
- 버튼 문구는 동작을 나타내는 동사형을 우선합니다.
- 아이콘만 있는 버튼은 accessible label 또는 tooltip을 제공합니다.
- hover에서는 배경·보더·텍스트 대비를 바꾸고, 기본적으로 큰 이동이나 확대를 사용하지 않습니다.
- loading 중에는 중복 실행을 막고 진행 중인 작업을 문구나 spinner로 표시합니다.

### 검색과 필터

- 검색은 화면의 주요 목적에 맞는 경우 가장 먼저 보이게 합니다.
- placeholder는 검색 대상과 예시를 구체적으로 설명합니다.
- 필터가 3개 이상이면 개별 컨트롤이 콘텐츠를 압도하지 않는지 확인하고 묶음 메뉴를 검토합니다.
- 활성 필터는 텍스트나 배지로 쉽게 식별할 수 있어야 합니다.
- 검색 결과 없음과 필터 결과 없음은 원인과 다음 행동을 각각 안내합니다.

### 탭과 segmented control

- 같은 수준의 보기 전환이나 모드 전환에만 사용합니다.
- 선택 상태는 배경색만이 아니라 텍스트 대비·보더·aria 상태로도 구분합니다.
- 탭 안에 너무 많은 작업 버튼을 넣지 않습니다. 작업은 별도 액션으로 분리합니다.

### 카드와 리스트 행

- 카드는 곡의 핵심 정보와 현재 상태를 빠르게 비교하는 데 사용합니다.
- 카드 안의 정보 우선순위는 썸네일·제목·아티스트·작업 상태 순으로 유지합니다.
- 배지는 `MR`, `가사 싱크`, `처리 중`처럼 실제 판단에 필요한 상태만 표시합니다.
- hover 확대·scale로 인접 콘텐츠를 밀어내지 않습니다.
- 리스트 행은 많은 곡을 빠르게 비교하거나 관리할 때 사용하며, 일괄 선택 상태를 명확히 표시합니다.

### 배지와 상태

- 상태 이름은 사용자가 이해할 수 있는 작업 언어로 씁니다.
- 처리 중에는 현재 작업과 진행률을 함께 표시합니다.
- 실패 상태에는 원인, 영향 범위, 재시도·수정·닫기 중 가능한 다음 행동을 표시합니다.
- 상태 배지를 장식처럼 모든 카드에 반복하지 않습니다.

### 토글·체크박스·슬라이더

- 토글은 즉시 적용되는 on/off 설정에 사용합니다.
- 체크박스는 여러 항목을 선택하거나 저장 전 확인하는 옵션에 사용합니다.
- 슬라이더는 값의 연속적인 조절이 의미 있을 때만 사용하며, 현재 값을 텍스트로도 표시합니다.
- focus ring을 제거하지 않습니다.
- 적용 범위와 즉시 적용 여부를 라벨 또는 보조 문구로 명시합니다.

### 드롭다운과 컨텍스트 메뉴

- 메뉴 항목은 동작 또는 선택지를 한 가지 의미로 표현합니다.
- 위험한 항목은 일반 항목과 시각적으로 구분하고 실수로 선택하기 어렵게 합니다.
- 메뉴가 열려 있는 동안 현재 대상과 메뉴의 관계가 분명해야 합니다.
- 메뉴 안에 긴 설명이나 설정 폼을 넣지 말고 모달·패널로 분리합니다.

### 모달과 대화상자

- 모달은 사용자의 현재 작업을 잠시 멈춰야 할 때만 사용합니다.
- 제목은 사용자가 결정해야 하는 내용을 요약합니다.
- primary·secondary·destructive 액션의 위치와 순서를 일관되게 유지합니다.
- 긴 설정은 모달 안에서 다시 여러 단계로 숨기지 말고 별도 화면이나 패널을 검토합니다.
- ESC, 바깥 영역 클릭, 닫기 버튼의 동작을 상황에 맞게 정의합니다.

### 알림·로딩·빈 상태·실패 상태

- 전역 알림은 작업 완료·실패·복구처럼 즉시 알려야 하는 결과에 사용합니다.
- 로딩 상태는 무한 spinner만 사용하지 말고 가능한 경우 단계·진행률·예상 작업을 표시합니다.
- 빈 상태에는 왜 비어 있는지와 첫 행동을 함께 보여줍니다.
- 실패 상태에는 사용자가 복구할 수 있는 행동을 제공합니다.
- 작업 큐에 들어간 작업은 화면을 이동해도 상태를 확인할 수 있어야 합니다.

### 하단 플레이어 도크

우선순위는 현재 곡 → 재생 상태 → 진행률 → 볼륨 → 부가 작업 순입니다.

- 현재 곡과 아티스트가 잘리지 않고 식별되어야 합니다.
- 재생·일시정지와 진행 위치는 가장 쉽게 접근할 수 있어야 합니다.
- AI 처리·오버레이·곡 관리 같은 부가 작업은 빠른 메뉴 또는 보조 영역으로 이동합니다.
- 향후 믹서가 추가될 수 있도록 플레이어 컨트롤과 트랙·라우팅 컨트롤을 구조적으로 분리합니다.

## 5. 화면별 UX 기준

### 라이브러리

- 첫 행동은 곡 검색·추가·재생 중 하나로 명확해야 합니다.
- 검색창은 주요 진입점으로 두고, 필터와 관리 기능이 곡 탐색을 압도하지 않게 합니다.
- 카드에는 실제 판단에 필요한 상태만 표시합니다.
- 그리드·리스트·버튼 모드 전환은 하나의 일관된 segmented control로 제공합니다.
- 일괄 선택·곡 관리는 일반 탐색과 구분되는 관리 모드로 표현합니다.

### 노래 추가

- 유튜브 URL, 로컬 파일, 통합 검색을 하나의 진입점에서 시작할 수 있게 합니다.
- `가져오기 → 정보 확인 → MR 분리 → 가사 싱크`의 진행 흐름을 사용자에게 보여줍니다.
- 기본값은 빠르게 진행할 수 있게 하고, 모델·경로·세부 옵션은 고급 설정으로 분리합니다.
- AI 처리는 작업 큐와 연결해 사용자가 현재 위치와 진행 상태를 잃지 않게 합니다.

### 플레이어

- 현재 곡, 재생 상태, 진행률, 볼륨을 우선 노출합니다.
- 부가 작업은 빠른 메뉴 또는 보조 영역으로 이동합니다.
- 플레이어와 향후 믹서 UI가 같은 공간을 무리하게 공유하지 않도록 확장 영역을 분리합니다.

### 가사 싱크

- 가사 텍스트, 파형, 재생 위치를 시각적으로 분리합니다.
- 자동 정렬·수동 보정·앵커 설정을 핵심 작업으로 정의합니다.
- 낮은 신뢰도의 줄만 검토 대상으로 강조하고 모든 줄을 같은 강도로 표시하지 않습니다.
- `자동 정렬`, `현재 줄 보정`, `저장`의 우선순위를 유지합니다.

### OBS 오버레이

- `미리보기 → 프리셋 → 세부 설정` 순서로 제공합니다.
- 프리셋은 빠른 선택용으로 유지하고, 세부 옵션은 접을 수 있는 고급 영역으로 구분합니다.
- 미리보기 상태와 실제 방송 상태의 차이를 명시합니다.
- 폰트·색상·투명도·애니메이션은 즉시 미리보기에 반영하되, 기본값을 쉽게 복원할 수 있어야 합니다.

## 6. 콘텐츠와 문구 기준

### 읽는 사람

OSW를 쓰는 사람은 **OBS로 방송하는 노래 스트리머와 커버 제작자**입니다.
이들은 이 도구를 스스로 찾아서 설치한 사람들이고, 이미 알고 있습니다:

- 볼륨, 모니터, 키, 빠르기(BPM), 페이더
- MR과 보컬, 원곡과 커버
- OBS의 장면·소스·브라우저 소스

**그러므로 이런 것을 설명하지 않습니다.** 아는 것을 풀어쓰면 친절한 게 아니라
읽는 시간을 뺏는 것입니다. 특히 라이브 화면은 공연 중에 눈으로 스치는
화면이라, 한 글자라도 줄이는 쪽이 더 배려하는 것입니다.

### 라벨

- **용어를 그대로 씁니다.** `모니터`이지 `내 귀에 들리는 소리`가 아닙니다.
  `출력 장치`이지 `소리 보내는 곳`이 아닙니다.
- 라벨은 명사구로 짧게. 문장으로 늘어놓지 않습니다.
- 값의 뜻은 눈금·단위로 보여주고 라벨에서 반복하지 않습니다.
  (`가이드 보컬` + 눈금 `반주만 ↔ 보컬 100`)

### 설명을 붙이는 경우

보조 설명은 **사용자가 짐작할 수 없는 것**에만 답니다.

- 이 앱에서만 통하는 동작 (예: 표시 항목을 끄면 방송 화면에서 사라짐)
- 되돌릴 수 없거나 방송에 바로 나가는 것
- 값이 어디서 왔는지 (예: 장르는 Last.fm, 키·BPM은 음원 분석)

반대로 아래는 붙이지 않습니다.

- 컨트롤 이름을 다시 풀어쓴 것 (`앨범 커버 썸네일`, `곡 제목 위의 작은 머리글`)
- 왜 쓰는지에 대한 추측 (`제목만 크게 띄우고 싶을 때 끕니다`)
- 조작 방법 중 자명한 것 (`끌어서 조절`)

### 그 밖

- 개발 용어와 내부 구현명은 사용자 문구에 직접 노출하지 않습니다.
- `AI가 처리 중`보다 `가사 싱크 준비 중`, `MR 분리 중`처럼 구체적인 작업을 사용합니다.
- 오류 메시지는 `원인 → 현재 영향 → 다음 행동` 순서로 작성합니다.
- 버튼은 `확인`보다 `저장`, `다시 시도`, `MR 분리 시작`처럼 결과를 설명하는 동사형을 사용합니다.
- 시간이 걸리는 동작은 누른 즉시 상태를 바꿉니다 (`중지` → `중지 중…`).
  눌렀는지 알 수 없으면 사용자는 다시 누릅니다.
- 툴팁은 기본 설명이 아니라 화면을 복잡하게 만들 수 있는 보충 설명에만 사용합니다.

## 7. 접근성과 반응형 기준

- 색상만으로 상태·선택·오류를 구분하지 않습니다.
- 키보드 focus 상태를 항상 제공합니다. 기본 focus ring을 제거할 때는 대체 표현을 함께 구현합니다.
- 아이콘 버튼에는 accessible label 또는 tooltip을 제공합니다.
- 본문·버튼·상태 텍스트의 대비를 테마별로 확인합니다.
- 주요 컨트롤은 마우스와 키보드 모두로 조작할 수 있어야 합니다.
- 1280px급 창에서도 곡 추가·검색·재생·핵심 상태가 가려지지 않아야 합니다.
- 가로 스크롤은 파형·트랙·대형 전문 편집 화면처럼 넓은 작업 공간이 본질적으로 필요한 경우에만 허용합니다.
- `prefers-reduced-motion` 사용자는 반복 애니메이션과 이동 효과를 줄여서 사용할 수 있어야 합니다.

## 9. 구현과 유지 방식

- 문서는 한국어로 유지하고, CSS 클래스명·토큰명은 실제 코드 표기를 병기합니다.
- 새로운 토큰을 추가하기 전에 기존 토큰으로 해결할 수 있는지 확인합니다.
- 디자인 토큰을 변경할 때는 이 문서와 `src/styles/base.css`를 함께 검토합니다.
- 새로운 화면을 추가할 때는 목적, 주요 행동, 로딩, 빈 상태, 오류 상태를 문서 기준에 맞춰 정의합니다.
- 새 컴포넌트는 기존 버튼·입력·배지·패널 패턴으로 재사용할 수 있는지 먼저 확인합니다.
- UI 리뷰에서 예외를 허용했다면 해당 화면의 이유와 범위를 PR 설명에 남깁니다.
- 이 문서는 기능 동작이나 데이터 구조를 정의하지 않습니다. 동작 계약은 코드·테스트·기능 문서를 기준으로 합니다.

## 10. 향후 확장 기준

믹서와 미니 DAW 기능을 추가할 때도 기존 UI 원칙을 유지합니다.

- 트랙·라우팅·페이더는 장식 카드보다 지속적인 상태 확인과 빠른 조작을 우선합니다.
- 오디오 미터·클리핑·지연·출력 장치 상태는 색상 외에 숫자나 텍스트로도 확인할 수 있어야 합니다.
- 라이브 방송용 조작과 녹음·편집용 조작은 모드로 구분하되, 공통 토큰과 컴포넌트를 공유합니다.
- 고급 기능을 추가할 때 기본 흐름의 주요 행동과 현재 재생 상태를 가리지 않습니다.

## 라이브 화면의 '다음 곡' 큐

**빈 상태로 시작하고, 사용자가 직접 담는다.** 라이브러리 전체나 현재 필터
결과를 자동으로 밀어 넣지 않는다. 방송 중에 부를 곡은 라이브러리에 있는 곡
전부가 아니라 그날 고른 몇 곡이기 때문이다.

- 큐가 비어 있을 때는 "담아 주세요"라고만 안내한다. 대신 채워 놓지 않는다.
- 큐에 담는 경로: 음원 관리 표에서 곡을 고르고 담기 / 라이브 화면에서 검색해
  담기.
- 큐는 재생 순서와 별개다. 큐를 비워도 재생은 계속된다.

### 나중에: 신청곡 자동 담기

시청자 신청곡을 큐에 자동으로 넣는 것이 다음 단계다. 설계 시 지킬 것:

- **자동으로 들어와도 큐의 주인은 진행자다.** 신청곡은 큐 끝에 "신청" 표시와
  함께 붙고, 순서 변경·삭제는 언제든 가능해야 한다. 자동으로 현재 곡을
  바꾸거나 맨 앞에 끼워 넣지 않는다.
- **신청자 이름을 같이 들고 다닌다.** 오버레이가 "신청: 달빛나그네"를 띄울 수
  있어야 한다(시안의 라이브 화면에 이미 그 자리가 있다).
- **라이브러리에 없는 곡 신청**을 어떻게 처리할지 먼저 정한다 — 자동 다운로드는
  분리·정렬 시간이 걸려 방송 중에 바로 부를 수 없다. 기본값은 "목록에 없음"
  표시이고, 담기는 진행자가 결정한다.
- 연동 대상(치지직·트위치·유튜브 채팅 등)은 각각 인증 방식이 달라, 큐에 넣는
  내부 인터페이스를 먼저 하나로 정하고 어댑터를 붙인다.

## 설정 화면: 하위 탭이 "긴 리스트"로 되돌아가는 재발 버그

이 화면은 두 번 리스트로 돌아갔다. 원인은 두 번 다 같았고, 둘 다 **설정과
무관한 작업**이 방아쇠였다.

### 원인 1 — 카테고리를 남의 버튼 id로 추론했다

`settings-tabs.js`가 이렇게 카테고리를 정했다:

```js
const SCAT_ANCHORS = { library: ['btn-open-manager'], ... };
// 그 id를 가진 요소의 .settings-group 조상에 data-scat을 붙인다
```

즉 **"가져오기·백업" 섹션이 자기 카테고리를 아는 근거가, 그 안에 있는
`btn-open-manager` 버튼**이었다. 그래서:

| 언제 | 무슨 일 | 결과 |
| :--- | :--- | :--- |
| 커밋 `fd8780b` | 곡 관리 버튼을 라이브러리 툴바로 옮김 | 앵커 사라짐 → 앵커를 `btn-import-spreadsheet`로 급히 교체 |
| 곡 정보 관리자 제거 | 그 버튼이 아예 없어짐 | 같은 고리 |

섹션이 카테고리를 잃으면 `sec.dataset.scat || DEFAULT_SCAT`에 걸려 **조용히
'일반'으로** 들어간다. 오류도 없고 테스트도 없어서, 설정 화면이 길어진 걸
사람이 눈으로 볼 때까지 아무도 몰랐다.

### 원인 2 — 탭 상태를 앱 시작 때 한 번만 칠했다

`initSettingsTabs()`는 부팅 시 1회만 돌았다. 그 뒤에 다른 코드가 섹션의
`hidden`을 건드리면(릴리즈 게이팅·모달 등) 되돌릴 기회가 없어 그대로 굳었다.

### 고친 방식

1. **카테고리는 마크업이 선언한다.** 각 `.settings-group`이 index.html에서
   `data-scat="general|media|ai|library|about"`을 직접 들고 있다. 추론은 없다.
   다른 화면에서 무엇을 지우든 설정 분류는 흔들리지 않는다.
2. **빠지면 시끄럽게 실패한다.** `data-scat`이 없는 섹션은 콘솔 error로
   알리고 `data-scat-missing` 표시를 남긴다. 조용히 '일반'으로 흘려보내지
   않는다.
3. **설정에 들어올 때마다 다시 적용한다.** `switchTab('settings')`이
   `refreshSettingsTabs()`를 부른다. 누가 중간에 `hidden`을 풀어도 다음 진입에
   복구된다(마지막에 보던 탭을 유지한다).
4. **테스트로 못을 박았다.** `tests/settings-tabs.test.js`가 index.html을 직접
   읽어 ① 모든 섹션에 `data-scat`이 있는지 ② 값이 알려진 카테고리인지
   ③ 빈 탭이 없는지 ④ 앵커 추론 코드가 되살아나지 않았는지 검사한다.

### 설정 섹션을 새로 추가할 때

```html
<section class="settings-group" data-scat="media">
```

`data-scat`을 빼먹으면 테스트가 실패한다. 카테고리를 새로 만들려면
`settings-tabs.js`의 `CATEGORIES`, 하위 탭 버튼, 이 문서를 함께 고친다.
